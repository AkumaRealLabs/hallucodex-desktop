# HalluCodex desktop account modules

English | [中文](README.zh.md)

This reference covers the native modules in [src/hallucodex](../src/hallucodex). They compose secure account restoration, authenticated model discovery, and a relay for the selected New API server. Every Windows, macOS, and Linux build, packaged or development, runs as HalluCodex without a switch. The server defaults to `https://api.hallucodex.com`; while signed out, a small link in the account dialog selects another New API site such as a test server, and saved credentials load only for the server that issued them. The branded profile disables upstream account, manual-key, and configurable-provider entries, and every DeepSeek-hosted service: feedback upload of session logs, DeepSeek web search, product telemetry, and the session-log, wire-extension, and package-inventory plugins that only serve DeepSeek routes. Its system prompt names the agent HalluCodex. The application menu and a sidebar entry above Settings open the native account dialog; its operations are limited to the owned primary frame. The desktop authorization endpoints are a separate New API integration; the modules do not reinterpret a dashboard JWT, PAT, or ordinary API key as a desktop grant.

## Native ownership

Construct `HalluCodexDesktopRuntime` in the Electron main process after `app.whenReady()` and after acquiring the application's single-instance lock. Supply `SafeStorageRefreshStore` in a dedicated directory under the app's trusted user-data directory, `HalluCodexHttpAuthTransport`, native `fetch`, and `shell.openExternal`. `getSnapshot`, `startSignIn`, `cancelSignIn`, `restore`, `refreshAccount`, `refreshCatalog`, `refreshWallet`, `selectGroup`, and `signOut` are the account UI operations. The shell validates its owned window and main-frame origin for every account IPC call. The preload renders only safe snapshots and localized copy, cancels sign-in when the dialog closes, and never exposes raw IPC or token readers. To the page it exposes only `window.dshHalluCodex`: a sign-in status with a display name, and an action that opens the dialog.

Opening the dialog while signed in re-reads the wallet and device usage, coalescing duplicate requests within the same revision. The dialog shows refresh progress and the last successful update time; failure retains the previous figures and time with a stale-data notice, while a first failure shows unavailable rather than zero. Sign-out, account or server changes, and group moves clear the previous identity's data. Amounts follow the display setting in the site's public `/api/status`: US dollars, yuan, or a custom unit at the configured rate, or raw quota, formatted like the New API web console. Until that status has been read, the dialog shows raw quota.

Errors cross IPC as fixed categories, without raw exceptions or arbitrary server messages. Account capabilities, catalog, and balance report failures independently and offer their own retries; network recovery can retry saved sign-in, while expired sign-in offers browser authorization. Balance reads rotate and retry at most once after a 401; an ordinary 403 or read failure does not itself sign out. Subscribed updates take precedence over older state queries, and disposal awaits tracked operations.

The trusted Host uses an authenticated IPv4 loopback relay to reach `invoke`. Its random local capability travels only over Node IPC, never configuration files, environment variables, renderer state, or session content. Each prepared request carries the account/catalog revision; a request prepared before an account or group change is rejected. It receives the response stream and the group/model captured at admission. The account broker's access resolver stays in the main process. Neither a session snapshot nor a YAML profile contains access or refresh tokens. The operating-system keyring and file permissions protect credentials at rest; they are not a security boundary against a compromised process running as the same operating-system user.

## Authorization and storage

Login opens the system browser with S256 PKCE, a random state, and an ephemeral `127.0.0.1` listener using `/oauth/callback`. The authorization page must stay on the selected server's origin. The callback contains the authorization code and state, or `error=access_denied` when the user denies access in the browser. The listener answers with a static page in the browser's language, styled by one hash-pinned inline style and running no script, and the desktop window returns to the front once the browser step ends. The refresh expiry check tolerates ten minutes of clock difference between the desktop and the server. Cancellation, expiry, sign-out, and newer attempts invalidate older work, including delayed network and storage results.

Access credentials remain in memory. Refresh-only records are atomically persisted in a private encrypted file. Linux requires a supported OS keyring backend; `basic_text`, unknown backends, and unavailable encryption fail closed. The account broker serializes storage operations and refresh rotation within the application instance. The caller's single-instance lock is required; the store does not provide cross-process coordination by itself.

The desktop service grants a concrete account-allowed group during browser authorization. When the server also grants `group:select`, the account dialog can move the device to another group the account may use: select a candidate, preview its full name, rate, and wrapping description separately, then press Switch group to submit. When `/groups` reports `auto` for the account, the list also offers auto, which routes each request through an ordered list of concrete groups and charges at the rate of the group that serves it. The device follows the complete global Auto order until the user checks and orders groups up to the site's `max_groups`; a custom order made from a longer global order keeps its first `max_groups` groups, Restore global Auto returns to the global order, and a checkbox, on by default, retries a failed request with the next group of the order. The grant reports the order in `auto_groups`, null while following the global order, and the retry choice in `cross_group_retry`. While auto is selected, the dialog shows the catalog's `route_groups` order and warns when none of its groups is usable now. Browser authorization grants only concrete groups, so auto is chosen in the dialog after sign-in. `POST /api/desktop/v1/group` rotates the refresh credential and rebinds the session, its routing, and its usage ledger in one step, keeping the device's usage and quota cap; saving another order or retry choice is a move too. Starting a move closes old-group admission for new requests without replaying existing streams; admission reopens only after the new catalog is read completely. A group the server refuses keeps the current group and login, and a successful move is reported separately from subsequent catalog or balance failures. Without `group:select` the group stays fixed, and changing it requires signing in again. There is no client-side group override.

Refresh account rotates credentials even before access expiry, synchronizing granted permissions and allowed groups before reading the catalog and balance; it is not a timer. Duplicate refreshes coalesce and serialize with group moves. An older server not granting `group:select` is not a refresh failure, and a catalog-only retry does not unconditionally rotate valid credentials. Expired or revoked credentials require sign-in. A refresh or group move that fails with a network error is retried once immediately, inside the server's short window for repeating a rotation whose response was lost; a further transient failure, including a server answer of `temporarily_unavailable`, does not erase a saved refresh grant or mark capability refresh as successful. Local sign-out blocks requests before revocation; its result separately reports whether remote revocation succeeded.

## Models and relay

Groups and models are fetched only from authenticated desktop APIs, with a 15-second deadline and a response-size limit per catalog request; a failed read cancels and awaits its sibling. Discovery rejects inherited groups, other spellings of `auto`, duplicates, malformed metadata, a catalog whose group or route order does not match the device routing, and a changed account; the auto catalog lists the models of every group in its order. It publishes models and reopens relay admission only after the complete account-bound read succeeds; catalog failure does not block the independent wallet read. Public pricing or status metadata cannot grant model access or change the service origin; the public status only decides how amounts are shown.

The relay supports advertised Chat Completions, Responses, and Anthropic Messages endpoints. `openai-response` and `openai-responses` normalize to `/v1/responses`. Unknown protocols remain unavailable; names do not imply protocol compatibility. Each request must select a catalog model and one of that model's advertised endpoints. Each model is listed once, under one advertised endpoint: the protocol of its matching vendor catalog entry described below, otherwise a protocol of that vendor's models sharing its leading letters such as `claude` or `gpt`, otherwise the first of Chat Completions, Responses, and Messages. The name match places a model newer than the installed catalog beside its siblings without offering reasoning levels. Three native providers reuse the existing pi-ai protocol serializers with automatic retries disabled. The Anthropic SDK's local x-api-key and exact beta query are translated at the private relay, and neither is forwarded as account authentication. Request-level `group`, `auto_groups`, and `cross_group_retry` fields are rejected, including values introduced by serialization.

Reasoning effort levels come from the installed pi-ai catalog. When a model's id and protocol both match an entry of a vendor-run pi-ai provider (Anthropic, OpenAI, xAI, Meta, DeepSeek, Moonshot AI, Kimi Coding, Z.ai, MiniMax, Xiaomi, Ant Ling, or Alibaba's Qwen Token Plan limited to its `qwen` models, first match wins), the model selector offers that entry's levels and requests use its thinking parameters and the related compatibility switches. Gateway catalogs are not consulted because their values target the gateway itself. Other models offer no levels. Choosing no level sends no reasoning parameter, so the upstream default applies. Other vendor switches keep pi-ai's detection.

Each model's context window and output limit come from the first available of: the user's values for that model; the values configured in the server's model metadata; the matching vendor catalog entry described above; and the server defaults of 128000 and 8192, which the catalog names in `capacity_defaults`. A server that does not publish `capacity_defaults` has all its values treated as configured. A user or server output limit caps every request, and compaction reserves room for it; an output limit from the vendor catalog only describes the model, and each request sends it reduced to the room left in the context window, as pi-ai does. When the output limit exceeds the context window, the lower-ranked of the two values changes to fit. The Context row of the composer's model menu shows the selected model's effective values and opens a pane with their sources, where the user sets either value; an empty field follows the automatic value, and Restore auto removes both. The Host provides the session controller's `modelCapacity` service for listed models and forwards each change to the main process, which saves it and republishes the configuration before the change completes. Each value is a positive integer up to 100,000,000, and the output limit cannot exceed the context window. The values apply to every conversation and are stored on this device for each server and model, in a private file in the user-data directory; they survive group switches and sign-out. A model with no server value and no catalog match is not listed, so its values cannot be set.

The relay omits browser cookies, rejects redirects, enforces the configured byte limit, and never automatically retries an inference request. A 401 means the server rejected the credential: admission closes, the access token is rotated through a fresh discovery, and a revoked device signs out. A 403 carries a business limit such as an exhausted wallet or device quota cap; it reaches the caller unchanged and the catalog stays available. A 429, a server error, or a network failure does not change groups or trigger a second billable request. Existing streams keep their original selection. Prices, balances, usage settlement, and channel routing remain server responsibilities.

## Updates and release notes

Updates come from this repository's public GitHub Releases on tags `hallucodex-v<semver>`; only published stable releases are offered. Nothing downloads or installs without the user's confirmation: every offer shows the release notes, taken from the release body up to the `<!-- hallucodex:install-notes -->` marker and shown as plain text. Windows and AppImage builds download in-app after that confirmation and ask again before restarting to install. macOS builds without a Developer ID signature, and deb installations, cannot be replaced in place, so the dialog opens the release page instead; such builds check once after launch and skip a release the user postponed, while the menu check always reports. No mandatory-update policy is packaged, so no update is ever forced.

## Verification and activation requirements

Focused keyless tests use mocked remote responses and real local callback listeners. Run the account, routing, amount display, model capacity, native dialog, model menu, and IPC checks with `vitest run apps/desktop/tests/hallucodex-auth.spec.ts apps/desktop/tests/hallucodex-routing.spec.ts apps/desktop/tests/hallucodex-quota-display.spec.ts apps/desktop/tests/hallucodex-model-capacity.spec.ts apps/desktop/tests/hallucodex-account-ui.client.spec.ts apps/desktop/tests/host-process.spec.ts apps/desktop/tests/main-startup.spec.ts apps/desktop-host/tests/hallucodex-provider.spec.ts packages/client/ui-model-selection/tests/model-select.client.spec.tsx --maxWorkers=2`. The dialog integration case connects the real account runtime and HTTP authorization transport, replacing only external dependencies such as network and storage; English and Chinese visible-state snapshots live in the desktop tests' `__snapshots__` directory. These do not verify a live account, a paid model call, actual OS keyring behavior, or an installed desktop build, and jsdom assertions are not real-browser visual qualification.

A branded release requires a New API server with this desktop authorization, its ServerAddress set to the public origin, and real installed qualification on Windows, macOS, and Linux. Switching groups in the app also needs a server version that grants `group:select`; auto also needs the site to include `auto` in the account's usable groups, and withdrawing it signs out devices that use it, as for any withdrawn group. Falling back to the vendor catalog for capacities the metadata leaves unset requires a server that publishes `capacity_defaults`. Packages read updates only from this repository's GitHub Releases and carry no mandatory-update policy; the inherited DeepSeek Harness feeds are not used. The Host adapter uses the normal model selector; its catalog publication refreshes existing composers. The first native launch seeds an unselected default through the writable profile, preserving later user model selections. When the catalog lists the saved default's model under another endpoint, the default moves there without its reasoning level. A session whose selected model is no longer listed asks for another model before sending. Packaging alone does not supply those integrations. Release publishing, real credentials, and production calls are separate operations.
